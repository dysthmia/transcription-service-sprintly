# transcription-service-sprintly

## Обработка 
1. Whisper (faster-whisper) *локально* - Обрабатывает MP3 и извлекает речь в текст.
2. Ollama + Qwen3 4B *локально* - Убирает слова-паразиты, исправляет пунктуацию и превращает транскрипцию в структурированный конспект Markdown.
3. Извлечение текста и OCR *локально* - TXT — чтение текста. DOCX — `python-docx`. PDF — `PyMuPDF`.JPG и изображения — `Tesseract OCR`.

## БД

> Нужно обеспечить идемпотентность, поэтому гарантия на уровне БД и продуманная обработка повторных сообщений.

PostgreSQL позволит хранить:
- идентификатор материала из PAPA;
- уникальный идентификатор задания;
- статус обработки;
- текущий этап пайплайна;
- количество попыток и сведения об ошибках;
- ключи исходного файла и результата в S3;
- время создания, начала и завершения обработки;
- версию пайплайна и моделей, если потребуется воспроизводимость результатов.

`processing_jobs`
``` txt
Поле	                Назначение
id	                    UUID задания
material_id	            ID материала в PAPA
source_event_id	        ID входящего события Kafka
source_object_key	    Ключ исходника в S3
source_version	        Версия исходника, если поддерживается
status	                Текущее состояние обработки
current_stage	        Этап, на котором находится обработка
attempt_count	        Число попыток
result_object_key	    Ключ готового Markdown в S3
error_code	            Код последней ошибки
created_at	            Время создания
started_at	            Время начала
completed_at	        Время завершения
```
`outbox_events`
``` txt
Поле		            Назначение
id		                ID события
job_id		            Ссылка на processing_jobs.id
event_type		        Например, material.processed
payload		            Тело события Kafka
status		            pending или published
attempt_count		    Число попыток публикации
next_retry_at	        Время следующей попытки
created_at		        Создание события
published_at		    Успешная публикация
```

`status` 
- `pending` — задание принято;
- `processing` — обработка выполняется;
- `retry_wait` — ожидается повтор;
- `completed` — результат сохранён;
- `failed` — исчерпаны попытки или произошла неисправимая ошибка.

> В идеале определить, что считать одним и тем же заданием. Например material_id + source_version + pipeline_version

## Как всё будет работать

1) **Прием события**:
    - Проверяем схему входящего сообщения.
    - Пытаемся создать `processing_jobs` с **уникальным ключом идемпотентности**.
    - Фиксируем транзакцию в **PostgreSQL**.
    - Подтверждаем обработку сообщения в **Kafka**.
2) **Выполнение пайплайна**:
    - Получаем исходник из **S3**.
    - Извлекаем текст.
    - Запускаем **Whisper** или **OCR**.
    - Очищаем текст.
    - Создаём **Markdown**.
    > По мере прохождения этапов обновляем статус задания.
3) **Сохранение результата**
    - Загружаем `.md` в **S3** по **детерминированному ключу**.
    - Повторная загрузка того же результата **не создаёт новый логический артефакт**.
    >  Идемпотентность обеспечивается детерминированным ключом.
4) **Фиксируем завершение и событие**
    В **одной транзакции PostgreSQL**:
    - отмечаем задание **завершённым**;
    - создаём запись в **`outbox_events`**.
    Далее отдельный **publisher**:
    - отправляет событие о готовом конспекте в **Kafka**;
    - помечает outbox-запись **опубликованной**.
    > Паттерн **Transactional Outbox** гарантирует, что событие не потеряется и не будет опубликовано дважды.
